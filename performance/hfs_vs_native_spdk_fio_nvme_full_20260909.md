# HFS 与原生 SPDK 的 NVMe FIO 全矩阵对比

**测试日期**：2026-09-09  
**测试主机**：VM `ubuntu`，8 vCPU，Linux 6.8.0-139-generic  
**FIO**：`fio-3.42-139-gae35`  
**HFS 构建副本**：`/root/code/HFS_BASE_SPDK/build/lib/libhfs.so`，环境记录的源码 hash 为 `a414d49916cc3f6bbbe12fc0eb79c05036d1c7cd`  
**SPDK**：`f0b63ed866f0e4d3c56e73bd4a98d0042956147a`，FIO engine 为 `/root/code/spdk/build/fio/spdk_bdev`  
**测试设备**：同一块 SPDK NVMe bdev `Nvme0n1`（PCI BDF `0000:0b:00.0`）

## 测试口径

- workload 为 `randrw`，读写比例 50/50，`direct=1`，文件大小 256 MiB，单项运行 10 秒。
- 块大小覆盖 4/8/16/32/64 KiB；每个块大小分别测试单队列和高并发两组。
- 单队列：HFS 使用 `numjobs=1`、同步 `psync`；原生 SPDK 使用 `iodepth=1`。
- 高并发：HFS 使用 `numjobs=32`；原生 SPDK 使用 `iodepth=32`。这是有效并发度对齐，不表示两条路径的线程/调度实现完全相同。
- HFS 通过 `LD_PRELOAD=build/lib/libhfs.so`，原生 SPDK 通过 `LD_PRELOAD=/root/code/spdk/build/fio/spdk_bdev` 和 `ioengine=spdk_bdev`。
- 脚本同时生成 ext4 控制组，但本报告只比较 HFS 和原生 SPDK；两组比较的 `errors` 均为 0。
- 远端原始结果目录：`/var/tmp/hfs-fio-nvme-full-20260909/{qd1,qd32}/`，其中包含 `environment.txt`、`summary.tsv` 和各块大小的 JSON 日志。

高并发下 HFS 总吞吐为原生 SPDK 的 **45.45%～84.66%**。8/16 KiB 出现最明显的排队放大：HFS p99 写延迟达到 5.73/5.80 ms，而 raw SPDK 为约 1.47/1.50 ms；64 KiB 的吞吐差距缩小到 15.34%，说明较大请求可以摊薄部分固定开销，但 HFS 的写尾延迟仍明显偏高。

## 结果归因

1. **单请求固定开销仍可见。** 单队列的 IOPS 差距集中在 24%～31%，说明 NVMe 设备不是唯一瓶颈，HFS 的 POSIX 入口、fd/open-file 查找、请求对象和同步完成等待仍占用了可观的每请求时间。
2. **高并发的中等块大小最容易触发排队。** 8/16 KiB 在 32 路并发下只有 raw 的 45%～48%，同时 p99 达到 4.6～5.8 ms。这个形态与 `rangeGate`/inode 区间竞争、owner 队列排队、每请求 completion 唤醒以及 bounce/DMA 路径的固定处理相符；不能简单归因于 NVMe 带宽不足。
3. **大块请求的吞吐差距收窄但延迟没有同步收敛。** 64 KiB 达到 84.66% raw 吞吐，但 HFS 写 p99 仍为 5.28 ms，说明吞吐已部分受设备服务时间主导，尾延迟仍由用户态队列和串行化路径决定。
4. **CPU 数据要谨慎解读。** 单队列 FIO 统计中 HFS 约使用 8.5%～13.6% 的 fio 进程 CPU，raw SPDK 约 100%；这是同步 POSIX 与单 SPDK reactor 的实现差异，并不等价于 HFS 消耗更少的总系统 CPU。32-job 组的 FIO 百分比还会被多个 job 的聚合口径影响，不能直接与 raw 单 job 的百分比作结论。
5. **正确性和稳定性没有问题。** 两组、所有块大小及读写方向的 `errors=0`，可以把本轮差距视为性能路径差异，而不是错误重试或测试失败造成的假象。

## 后续优化优先级

- 优先在 8/16 KiB、`numjobs=32` 场景复测 `rangeGate` 的 wait/hold、writer-priority 排队和 owner queue wait，确认 p99 的主要占比。
- 将同步 POSIX 路径继续下沉到已注册 DMA 的 direct async 提交队列，减少 bounce copy、单请求 waiter 和一次请求一次通知。
- 按 inode/区间维护真正可并行的提交队列，避免多个不重叠请求在同一 owner 或元数据发布阶段串行化。
- 用固定 CPU 亲和、相同 reactor 数和更长重复轮次复测；本报告的 10 秒短样本用于回归定位，不应直接当作硬件绝对规格。

## 复现入口

使用 `scripts/performance/fio_stage2_compare.sh`。本轮新增 `HFS_FIO_SPDK_IODEPTH` 参数，使 raw SPDK 的 iodepth 可以与 HFS 的 `HFS_FIO_NUMJOBS` 配对，例如：

```bash
HFS_FIO_CONFIG=config/hfs_nvme.json \
HFS_FIO_BDEV_NAME=Nvme0n1 \
HFS_FIO_SPDK_BDEV_NAME=Nvme0n1 \
HFS_FIO_NUMJOBS=32 \
HFS_FIO_SPDK_IODEPTH=32 \
HFS_FIO_SIZE=256m \
HFS_FIO_RUNTIME_SECONDS=10 \
HFS_FIO_RUN_SPDK_REFERENCE=1 \
./scripts/performance/fio_stage2_compare.sh /var/tmp/hfs-fio-nvme-full-20260909/qd32
```
