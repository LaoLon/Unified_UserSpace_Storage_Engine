# HFS 第二阶段性能定位与优化任务单

## 0. 本阶段原则

上一阶段已经完成 P0-1 profiling 和 P0-2 部分层级基线。

本阶段不要直接按照旧结论开始大规模修改 completion/reactor。

现有数据出现了几个必须先进一步确认的问题：

```text
T1-T2 p99:
randread  ≈ 247 us
randwrite ≈ 208 us

T4-T5 p99:
randread  ≈ 205 us
randwrite ≈ 331 us

T8-T9 p99:
randread  ≈ 310 us
randwrite ≈ 272 us

T9-T10 p99:
randread  ≈ 335 us
randwrite ≈ 247 us
```

同时：

```text
randread ticket conflict = 0
randwrite real ticket wait = 425

ticket scan items:
read  = 7,651,226 / 265,816 requests
write = 6,290,887 / 213,447 requests
```

即每次请求大约扫描接近 30 个 active ticket。

因此当前最需要验证的是：

```text
ticket scheduler 固定成本
CPU oversubscription / scheduler latency
reactor queue latency
```

而不是先假定 futex 本身就是最大瓶颈。

# P0-1：修复并验证 A3 HFS internal benchmark

这是必须先完成的基线修复。

当前结果：

```text
A3 randread:

1 worker  = 83,178 IOPS
8 workers = 62,616 IOPS
32 worker = 83,178 IOPS
64 worker = 91,749 IOPS
```

其中：

```text
1 worker == 32 workers
```

数值完全相同，且：

```text
A3 internal 32 workers = 83k

A4 full POSIX 32 workers = 92k
```

这与逐层剥离开销的预期不一致。

## 任务 1.1

审计：

```text
HFS_INTERNAL_BENCH
```

实际实现。

确认：

1. worker 参数是否真的创建对应数量 worker；
2. 每个 worker 是否真的持续提交 I/O；
3. worker 是否拥有独立 request；
4. 是否意外共享一个同步执行线程；
5. 是否存在结果复用；
6. 是否存在固定 runtime/operation count 导致统计错误；
7. worker=1/8/32/64 是否真正产生不同 outstanding；
8. 每个 worker 是否最终仍同步 wait；
9. reactor selection 是否真的发生变化；
10. IOPS 计算公式是否正确。

输出：

```text
actual worker count
actual request count
actual SPDK submit count
outstanding peak
reactor distribution
runtime seconds
calculated IOPS
```

必须满足：

```text
IOPS = total_completed / actual_runtime
```

# P0-2：做 CPU concurrency / scheduler scaling 实验

这是决定 completion 优化之前的必要实验。

当前环境：

```text
8 vCPU

SPDK:
1 owner reactor
4 data reactors

FIO:
32 synchronous POSIX workers
```

这意味着可能存在超过 30 个 runnable application thread 与 SPDK reactor 争抢 8 个 vCPU。

因此当前：

```text
T4-T5
T8-T9
```

都可能被 CPU oversubscription 放大。

# P0-3：把 Ticket Scheduler 完整拆开测

这是当前最重要的软件路径分析任务。

目前仅知道：

```text
conflict 很少
```

但这并不代表 ticket 开销很低。

当前 ticket 每个请求都会：

```text
lock ticketLock
↓
扫描 active ticket list
↓
insert
↓
unlock

...

lock ticketLock
↓
remove
↓
扫描后续 ticket
↓
dependency update
↓
unlock
```

---

## 任务 3.1

把 T1-T2 拆成：

```text
TA0 ticket entry

TA1 ticketLock acquired

TA2 conflict scan complete

TA3 ticket inserted

TA4 waitReady complete
```

记录：

```text

ticket_scan
ticket_insert
ticket_dependency_wait
```

分别输出：

```text
avg
p50
p95
p99
```

---

## 任务 3.2

把 T9-T10 拆开。

write 请求尤其重要，因为 write 没有 copy-out。

增加：

```text
TC0 application wait returned

TC1 DMA lease released

TC2 ticket complete entered

TC3 ticketLock acquired

TC4 successor scan complete

TC5 ticket removed / wake processing complete

TC6 syncLock released

TC7 write-end publication complete

TC8 fd release complete
```

read 再增加：

```text
copy-out begin/end
```

最终回答：

```text

到底消耗在哪里？
```

## 判断规则

### 情况 A

如果：

```text
none >> ticket
range ≈ none
```

说明 ticket scheduler 是主要固定开销。

下一阶段优先改 ordering。

### 情况 B

如果：

```text
ticket ≈ range ≈ none
```

则 ticket 不是主要瓶颈。

停止优化 ticket。

# 最终目标

我们最终希望把当前路径：

```text
POSIX
 ↓
ticket global-per-inode scheduling
 ↓
mutex/message queue
 ↓
SPDK
 ↓
futex scheduler boundary
```

逐步缩短。

但每一项必须先证明：

```text
它确实占用可观性能
```

之后再修改正式 HFS 架构。

当前阶段的核心问题不是“怎么优化”，而是：

```text
在 4K / 32 synchronous worker 场景下，

200~300 us 级的软件尾延迟

究竟来自：

ticket？
reactor queue？
CPU oversubscription？
completion scheduling？
```

先回答这个问题，再进入正式数据面重构。
