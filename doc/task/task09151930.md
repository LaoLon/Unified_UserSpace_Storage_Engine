# HFS 第三阶段 Reactor / Backend 并发优化任务单

## 0. 本阶段核心结论

上一阶段数据已经排除或降低了部分嫌疑：

### Ticket 暂不作为主优化对象

ticket/range/none 对 steady-state IOPS 的差异较小：

```text
read 32:
ticket 89.9k
range  92.4k
none   91.1k

write 32:
ticket 68.4k
range  68.9k
none   69.1k
```

因此：

```text
不要重构 ticket scheduler。
```

现有 ticket lock/scan 开销可以后续优化，但不属于当前 P0。

---

### Open-file/metadata 暂不处理

T0-T1 很小，不是当前主要问题。

---

### 当前最重要现象

随着同步 worker 增长：

```text
T6-T7:
read:
1 job   43 us
8 job  116 us
16 job 170 us
32 job 340 us

write:
1 job   48 us
8 job  134 us
16 job 230 us
32 job 480 us
```

T6-T7 定义为：

```text
spdk_blob_io_read/write submit
        ↓
SPDK completion callback
```

它不是 POSIX wake latency。

其中可能包含：

```text
Blobstore queue
bdev queue
NVMe queue
per-reactor io_channel
NVMe qpair
device latency
completion polling delay
reactor scheduling
```

需要进一步拆分。

---

### Reactor 数量是当前最强性能信号

固定 CPU affinity 条件：

```text
owner = CPU0
application = CPU5-7
```

结果：

```text
            2 reactor       4 reactor

read         108.7k           87.4k
write         90.6k           67.9k

CPU read       445%            657%
CPU write      428%            629%
```

2 reactor 相比 4 reactor：

```text
read  ≈ +24%
write ≈ +33%
```

同时 CPU 显著降低。

因此第三阶段首先研究：

```text
为什么 data reactor 增加反而导致 SPDK backend latency 上升？
```

## 1.1 第一组：固定 application CPU

为了只研究 data reactor 数的影响：

```text

```


因此低 reactor 数时允许：


不要把这些空闲 CPU 分给 application，否则会同时改变两个变量。

该矩阵回答：

```text

是否影响 backend latency？
```

## 2.1 HFS submit 本身

增加：

```text
TB0 = hfsIoStart entry

TB1 = immediately before spdk_blob_io_read/write

TB2 = immediately after spdk_blob_io_read/write returns
```

统计：

```text
TB0-TB1
TB1-TB2
```

如果只有 ns/us 级，则排除 HFS submit wrapper。

## 2.2 每个 request 保存 backend 信息

记录：

```text

reactor inflight at completion

global outstanding at completion
```

必须区分每个 data reactor。

## 判断规则

如果 raw Blobstore 也出现：

```text
1 channel > 2 channel > 4 channel
```

或者：

```text
2 channel > 4 channel
```

说明问题主要不是 HFS。

而是：

```text
当前 NVMe / VM / SPDK backend
对多 channel/qpair scaling 不好
```

HFS 应该根据硬件调整 reactor/channel 数。

---

如果：

```text
raw Blobstore:
4 channel >= 2 channel

但 HFS:
2 reactor >> 4 reactor
```

则问题在 HFS：

```text
reactor scheduling
ingress
channel usage
completion
```

继续进入 P0-5。

# P0-5：区分 Device Latency 和 Completion Poll Delay

T6-T7 当前混合了：

```text
设备完成时间
+
reactor 发现 completion 的时间
```

需要尽可能拆开。

如果 SPDK trace 可以获得 NVMe CQ completion：

定义：

```text
TN0 = NVMe command submit
TN1 = NVMe completion observed by NVMe driver
TN2 = HFS hfsIoDone callback
```

这样：

```text
TN1-TN0
≈ NVMe/backend service

TN2-TN1
≈ SPDK completion propagation
```

---

如果无法直接获得 TN1：

至少统计 data reactor poll loop：

```text
last_poll_enter
last_poll_exit
poll gap
```

在 callback 时记录：

```text
time_since_last_poll
```

检查 4-reactor 情况是否存在异常 poll gap。

---

# P0-6：重新定义当前最佳并发点

不要继续默认：

```text
numjobs=32
```

就是 HFS 最重要 benchmark。

现有数据已经表明：

```text
read:
16 jobs = 87.8k
32 jobs = 87.2k

write:
16 jobs = 70.0k
32 jobs = 68.0k
```

因此当前性能 knee 在：

```text
约 16 synchronous workers
```

后续正式性能报告必须同时包含：

```text
jobs=16
jobs=32
```

其中：

```text
16 = throughput knee / practical configuration

32 = overload / tail-latency stress
```

不能只用 32 jobs 优化，然后宣称系统整体性能更优。

# P1：Completion wait 暂缓正式修改

当前：

```text
T8-T9

jobs=1:
≈18 us

jobs=32:
≈100 us
```

说明它明显受并发/CPU 调度影响。

因此在 reactor topology 稳定前：

```text
不要正式实现 adaptive spin。
不要实现 pure spin。
不要做复杂 wake batching。
```

完成 P0-1～P0-5 后，再重新测：

```text
T8-T9
```

如果使用最佳 reactor 配置以后仍然：

```text
> 30-50 us
```

再进入 completion 优化。
