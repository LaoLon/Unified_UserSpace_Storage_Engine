# HFS 2.0 MySQL Shard-104/105 当前 VM 验证

日期：2026-09-25。范围：MySQL 8.0.46 InnoDB frontend 的功能、崩溃恢复、
性能与 HFS/RocksDB 回归。执行入口为 `mysql/run_shard104_vm.sh`、
`mysql/run_shard104_crash_vm.sh`、`mysql/run_shard105_vm.sh`、
`mysql/run_shard105_diagnostics_vm.sh`、`mysql/run_shard105_gate_vm.sh`。
原始测试产物保存在 VM 本地 `/home/hfs/mysql-shard104-*`、
`/home/hfs/mysql-shard105-*`，不进入 Git。

## 环境和构建

- VM：6 vCPU、约 7.2 GiB RAM；目标控制器序列号 `VMware NVME_0002`，
  PCI `0000:13:00.0`，绑定 `uio_pci_generic`；`HugePages_Total=1024`。
- SPDK 锁定 `f0b63ed866f0e4d3c56e73bd4a98d0042956147a`；MySQL fork
  锁定 `mysql-8.0.46` (`0a7df2e4693d8f10901a26034ae6257699356e30`)，
  在 VM 内通过 Git 取得并按 base、guard、metrics 顺序应用补丁。
- HFS CMake Release、Make `app` 构建通过；MySQL `mysqld`、`mysql`、
  `mysqladmin`、`mysqlslap`、`mysqldump`、`mysqlcheck` 构建通过。
- HFS 正式配置为 `.conf`，单盘 `Nvme0n1`。MySQL 使用独立的
  `config/hfs_mysql.conf`。以下性能运行的 `stats=false`，只有设备 I/O
  归因诊断使用 `stats=true`。

## Shard-104 功能和恢复

`run_shard104_vm.sh` 通过初始化、SQL CRUD、事务回滚/提交、Read Committed
和 Repeatable Read、在线索引和 instant 列 DDL、外键、全文及空间索引、binlog、
`mysqlcheck`、`mysqldump`/逻辑恢复和跨进程 reopen。页压缩、clone、
MyISAM/Aria、`--daemonize`、native AIO、缺少 MyISAM 禁用参数和无效 HFS
配置均被拒绝。无效配置的宿主 datadir 保持空目录；`hfsctl check` 为
`corruption=none`。

`run_shard104_crash_vm.sh` 在 131072 行数据上确认在线索引 DDL 和并发写入
仍活跃时 SIGKILL；重启后行数保持、`CHECK TABLE` 为 `OK`。随后在页更新
仍活跃时再次 SIGKILL，重启后行数、`CHECK TABLE` 和 HFS 元数据检查均通过。
这是两处实测断点，不代表对所有掉电时序的穷尽验证。

## Shard-105 MySQL 性能与 durability

同一 VM 上按 HFS、native、HFS、native 顺序交错运行相同 MySQL 二进制，
每轮 8 线程、10 秒 sysbench OLTP 读/读写，另运行 mysqlslap 查询/更新。
`innodb_flush_log_at_trx_commit=1` 在各轮确认；延迟 p50 由完整 histogram
计算，p99 来自 sysbench 输出。

| 顺序 | 读 TPS | 读 p50/p99 ms | 读写 TPS | 读写 p50/p99 ms | mysqlslap 读/写秒 | redo fsync 增量 |
|---|---:|---:|---:|---:|---:|---:|
| HFS 1 | 11310.29 | 0.654 / 1.55 | 1560.53 | 4.823 / 9.91 | 0.053 / 12.173 | 43894 |
| native 1 | 11558.70 | 0.630 / 1.58 | 2274.38 | 3.364 / 7.04 | 0.054 / 10.735 | 73519 |
| HFS 2 | 10899.39 | 0.677 / 1.64 | 1939.85 | 3.885 / 8.13 | 0.056 / 11.083 | 47074 |
| native 2 | 12017.55 | 0.587 / 1.52 | 2262.81 | 3.364 / 7.30 | 0.061 / 10.762 | 71909 |

两轮均值比：HFS/native 读约 94.2%，读写约 77.2%。native datadir 位于
VM 根盘 ext4，HFS 位于独占测试 NVMe；此对照体现当前 VM 的端到端差异，
不能单独归因为 HFS 软件开销。每轮保留 CPU 线程映射、原始 histogram 与
fsync 前后计数。读写测试的 fsync 计数增长证明 redo fsync 路径在运行；
它不能单独证明每个事务的持久性，恢复验证见上节。

独立 `stats=true` 诊断运行中，SPDK data bdev 计数为读 23031 次、
149762048 字节，写 24277 次、298672128 字节；读/读写负载分别约
11865/1999.84 TPS。计数只覆盖 SPDK 接受的 DataPath I/O，不含 metadata、
journal、设备内部写放大。正式性能数据维持 `stats=false`。

当前 MySQL 读吞吐接近 native 参考，写入没有显示需要立即改变共享 core
durability 语义的证据。本 shard 保留现有 namespace barrier，未实施
data-only `datasync`；后续如果重做该优化，必须单独验证 `File::sync` 契约
和 RocksDB L4。

## HFS、RocksDB 与 FIO 回归

- CTest 串行 26/26 通过。硬件测试占用同一独占 bdev，故使用 `-j1`。
- FIO 3.42 HFS 4K randrw smoke：errors=0，queued/completed/reaped
  均为 194969，outstanding=0；32 MiB CRC32C 写入验证通过。
- RocksDB 9.11.2 `readrandom`，同 VM、8 线程、524288 keys、1024 B value、
  32 MiB cache：core 计数改动前 HFS 为 73240.8、73133.6 ops/s；改动后
  HFS 为 74221.9 ops/s。native 对应为 55445.8、54996.4 和
  55608.7、55240.6 ops/s。HFS 两轮改动前均值与改动后结果的差异约
  +1.4%，未观察到 L3 回退。
- RocksDB L4 小规模功能 smoke：fillseq、readrandom、overwrite、
  readwhilewriting 均成功；该 20000-key smoke 不作为正式吞吐比较。
- FIO 正式 8j4：4K randrw 50/50、256 MiB、每组 10 秒，raw SPDK
  1j32 与 HFS 8j4 交替共五组，均在同一测试 NVMe 上运行。五组 raw
  IOPS 为 136396、135901、134676、136967、136749；HFS IOPS 为
  88571、88660、88998、88295、89837；HFS/raw 分别为 64.94%、
  65.24%、66.08%、64.46%、65.69%，中位数 65.24%。全部 fio
  error=0，HFS queued=reaped、outstanding=0、token mismatch=0。

为检验本次 `SpdkRuntime` 统计分支是否造成 L4 回退，在 VM 独立源码/构建目录
中用 Git `HEAD` 的改动前 `src/runtime/spdk_runtime.cpp` 重建同一 HFS；
除该文件外复用当前源码、同一 SPDK 和配置。以相同脚本、同一 NVMe 再跑五组，
改动前 raw IOPS 为 135934、136695、136439、135425、135835；HFS 为
89457、88571、87830、89230、88408。改动前 HFS IOPS 中位数
88571，改动后为 88660，差异约 +0.10%；改动前 HFS/raw 中位数
65.08%，改动后 65.24%。改动前五组也全部 errors=0、closure 闭合。
因此，本次 core 统计改动的同机 L4 吞吐未观察到 >5% 回退。

五组读/写 p99 的中位数均为 raw 395.264 µs、HFS 452.608 µs，
约为 raw 的 114.5%，也高于 §16.2 的 110% 目标。fio JSON 的 CPU
字段仅代表 fio 工作线程，未覆盖 HFS/SPDK 后台线程，不能据此宣称总 CPU
满足 §16.2 门槛；本轮未采集完整进程级 CPU gate。

五组 8j4 未达到 `hfs2.0.md` §16.2 的 HFS/raw ≥85% 总体性能目标。
改动前后同机基线表明本次改动没有造成明显回退，但不能把与旧 VM 历史
成绩的差别解释为同一环境的回退。85% 吞吐、110% p99 和完整进程 CPU
门禁仍需后续性能工作；不以 MySQL 功能通过掩盖这些目标。
